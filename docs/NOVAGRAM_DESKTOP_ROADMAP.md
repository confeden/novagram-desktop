# NovaGram Desktop: развитие конфиденциальности и безопасности

> Статус: активная поэтапная реализация
> Платформа: Windows, база `telegramdesktop/tdesktop v7.0.8`, ветка `novagram/v7.0.7`
> Последнее обновление: 2026-08-03

Этот документ — план и источник достоверной информации о состоянии функций
конфиденциальности NovaGram Desktop. Он повторяет структуру и обозначения
статусов Android-документа
`android/novagram-android/docs/NOVAGRAM_PRIVACY_ROADMAP.md` и должен
обновляться в том же изменении, что и код.

Документация ведётся на русском языке. Названия API, классов, протоколов и
собственные имена остаются на английском.

## Преимущества по сравнению с официальным клиентом Telegram

Раздел отвечает на вопрос «зачем NovaGram, если есть официальный клиент».
Перечислено только то, что уже работает в коде; запланированное сюда не
попадает до статуса `Реализовано`.

### Windows Hello больше не обходит защиту

Это главное отличие в модели угроз и одновременно исправление реальной дыры.

В официальном клиенте локальный passcode можно заменить системной
разблокировкой: включив «Разблокировка с помощью Windows Hello», пользователь
получает вход по лицу, отпечатку или PIN-коду Windows. Для обычного сценария
это удобно, но для модели угроз NovaGram — провал:

- под принуждением у владельца берут палец или заставляют посмотреть в камеру,
  и passcode вообще не участвует;
- Windows Hello авторизует пользователя Windows, а не владельца переписки:
  любой, кто уже вошёл в сеанс Windows, открывает клиент без passcode;
- аварийный PIN становится бесполезным: сценарий уничтожения данных
  запускается только при вводе PIN, а системная разблокировка проходит мимо
  этого пути целиком.

В NovaGram при включённом режиме PIN системная разблокировка не предлагается
на экране блокировки, автоматически выключается при установке основного PIN и
скрывается из настроек. Единственный способ войти — ввести PIN, а значит
аварийный PIN всегда остаётся доступным вариантом.

### Остальные отличия

| Возможность | Официальный клиент | NovaGram |
| --- | --- | --- |
| Аварийный PIN | нет | ввод вместо основного уничтожает локальные данные и выходит из аккаунтов |
| Уничтожение данных | только выход из аккаунта, шифротекст остаётся на диске | на холодном старте `tdata` очищается физически, затем генерируется новый ключ |
| Защита от перебора | счётчик в памяти, обнуляется перезапуском | счётчик и задержка в файле, переживают перезапуск и перевод часов назад |
| Ввод кода | обычное поле, длина видна по точкам | `NoEcho`: не видно ни цифр, ни длины |
| Экранная клавиатура | нет | есть, порядок цифр случайный при каждом показе |
| Язык экрана блокировки | язык из языкового пакета, до разблокировки часто английский | русский текст доступен всегда, независимо от загрузки пакета |
| Захват экрана | окно снимается и записывается как обычное | окна исключены из захвата, снимок и запись не видят переписку |
| Ночной беззвучный режим | только ручной выбор при отправке | автоматически с 22:00 до 07:00, отдельно для диалогов, групп и каналов |
| Настройки форка | — | собраны в один раздел, а не разбросаны по чужим разделам |

Границы, которые важно называть честно: NovaGram не меняет серверные гарантии
Telegram. Облачная история, копии сообщений у собеседников и метаданные на
стороне сервера не затрагиваются ничем из перечисленного.

## Как устроен PIN в desktop-сборке

### Отличие от Android

На Android PIN — это отдельный шлюз перед запуском Telegram, а его
проверочные данные лежат в контейнере, запечатанном ключом Android Keystore.
В Telegram Desktop локальный passcode устроен принципиально иначе и сильнее:
он не хранится вообще, даже в виде хэша. Случайный `_localKey` (256 байт)
зашифрован ключом, выведенным из passcode через PBKDF2-HMAC-SHA512 со 100 000
итераций (`Storage::details::CreateLocalKey`,
`Telegram/SourceFiles/storage/details/storage_file_utilities.cpp`). «PIN верный»
означает «выведенный ключ расшифровал `tdata/key_data`».

Поэтому NovaGram Desktop не строит собственный шлюз, а делает основной PIN
этим самым passcode. Это даёт настоящее шифрование локальных данных ключом,
выведенным из PIN, вместо программной проверки поверх незашифрованных данных.

### Основной PIN

**Статус:** `Реализовано`

- Устанавливается в `Настройки → NovaGram → PIN NovaGram`.
- Ровно 4–6 цифр, проверка в `NovaGram::ValidPin`.
- Вводится в поле с `QLineEdit::NoEcho`: не показываются ни цифры, ни длина.
- Установка вызывает `Storage::Domain::setPasscode` и
  `Core::App().localPasscodeChanged()`, то есть переиспользует upstream-путь
  перешифрования `_localKey` и не создаёт второй копии ключа.
- Отдельно сохраняется флаг режима `pinModeEnabled` в `tdata/novagram_pin`,
  по которому экран блокировки переключается в режим NovaGram.
- Основной PIN обязан отличаться от аварийного; проверка выполняется при
  установке обоих.

### Аварийный PIN

**Статус:** `Реализовано`

- Устанавливается только при заданном основном PIN и требует его подтверждения.
- Верификатор: PBKDF2-HMAC-SHA512, 200 000 итераций, случайная 32-байтная соль,
  64-байтный результат; сравнение выполняется за постоянное время.
- Хранится в `tdata/novagram_pin`. Этот файл читается до разблокировки, поэтому
  аварийный PIN распознаётся уже на холодном старте, когда `_localKey` ещё не
  расшифрован.
- Ввод аварийного PIN на экране блокировки не разблокирует приложение, а
  вызывает `NovaGram::RunEmergencyWipe`: удаляется состояние PIN, удаляются
  файлы данных и вызывается `Core::App().logoutWithChecks(nullptr)`.
  - На холодном старте `NovaGram::WipeLocalData()` удаляет из `tdata` всё,
    кроме служебных каталогов `temp` и `tdummy`, после чего
    `Main::Domain::resetWithForgottenPasscode()` →
    `Storage::Domain::startFromScratch()` генерирует новый `_localKey` и
    записывает новый `tdata/key_data`. Прежний ключ становится
    невосстановимым, а шифротекста на диске уже не остаётся.
  - В разблокированной сессии это выход из каждого аккаунта, включая серверный
    `auth.logOut` по мере доступности сети, и `Storage::Account::reset()`.

#### Что показала проверка 2026-08-03

Пользователь установил основной и аварийный PIN и ввёл аварийный на холодном
старте `out/NovaGram.exe`. Разбор состояния после срабатывания:

- `tdata/novagram_pin` удалён, режим PIN выключен — приложение выглядит как
  установленное заново;
- `tdata/key_data` перезаписан в 06:47 новым случайным `_localKey`,
  зашифрованным пустым passcode;
- в `log.txt` записано `could not decrypt map` — это прямое доказательство, что
  прежний ключ уничтожен и старые данные аккаунта больше не расшифровываются;
- выход из аккаунта выполнен.

При этом обнаружено ограничение, которое и было устранено этим изменением: на
диске оставалось около 104 МБ шифротекста — `tdata/user_data/cache`,
`tdata/user_data/media_cache`, файлы аккаунта `tdata/<HEX>` и `tdata/<HEX>s`.
Данные были криптографически недоступны, но физически присутствовали: это
опровергало версию «приложением не пользовались» и оставляло материал для
будущей атаки на шифр. Теперь на холодном старте файлы удаляются до генерации
нового ключа.

Честная граница: если аварийный PIN вводится не на холодном старте, а после
автоблокировки работающей сессии, базы кэша открыты и Windows не даёт их
удалить. В этом случае работает только upstream-очистка
`Storage::Account::reset()`, а часть шифротекста остаётся. Закрытие этого
разрыва — отдельный пункт плана.

### Защита от перебора

**Статус:** `Реализовано`, но слабее Android

Формула повторяет Android: первые две ошибки без задержки, третья даёт 5 минут,
каждая следующая добавляет 5 минут, максимум 24 часа.

```text
failedAttempts < 3: delay = 0
failedAttempts >= 3: delay = min((failedAttempts - 2) * 5 минут, 24 часа)
```

Счётчик и срок хранятся в `tdata/novagram_pin` и переживают перезапуск, в
отличие от upstream-счётчиков `cPasscodeBadTries`, живущих только в памяти.
Перевод системных часов назад не сокращает задержку: обнаружив, что текущее
время меньше момента начала блокировки, NovaGram перезапускает полную задержку.

Честные границы: файл `tdata/novagram_pin` не привязан к оборудованию, поэтому
пользователь с доступом к диску может удалить его и сбросить счётчик. Это не
ослабляет шифрование: перебор всё равно упирается в PBKDF2 со 100 000 итераций
на каждую попытку. Аппаратная привязка состояния (DPAPI или TPM) — отдельный
следующий этап.

### Запрет системной разблокировки

**Статус:** `Реализовано`

Upstream позволяет разблокировать приложение через Windows Hello, Touch ID или
Apple Watch. В режиме PIN это была дыра в замысле: разблокировка проходила без
ввода PIN и полностью минуя проверку аварийного PIN, то есть под принуждением
владельца достаточно было приложить палец, и аварийный сценарий не запускался.

Закрыто в трёх местах:

1. `PasscodeLockWidget` при `_novaPinMode` вообще не создаёт ветку системной
   разблокировки, поэтому ни кнопки, ни автоматического запроса не появляется;
2. установка основного PIN выключает `systemUnlockEnabled` и сохраняет
   настройки, чтобы состояние настройки соответствовало поведению;
3. в `settings_local_passcode.cpp` блок переключателя скрывается при включённом
   режиме PIN, чтобы не показывать переключатель, который ничего не меняет.

### Перемешанная экранная клавиатура

**Статус:** `Реализовано`

`NovaGram::PinKeypad` (`Telegram/SourceFiles/novagram/nova_keypad.{h,cpp}`) —
сетка 3 × 4: девять цифр в первых трёх рядах, в нижнем ряду «Стереть», десятая
цифра и «Ввод». Порядок цифр перемешивается методом Фишера—Йетса на источнике
`base::RandomIndex`, то есть на том же CSPRNG, что и остальная криптография
приложения, а не на `qrand`.

Перемешивание выполняется при создании виджета и после каждой неудачной
попытки, но не после каждого нажатия: иначе ввод стал бы неприменимым.

Смысл: при фиксированной раскладке PIN восстанавливается по траектории курсора,
по записи экрана и по следам на сенсорном экране, даже когда сами цифры скрыты.
Случайный порядок обесценивает все три канала.

Клавиатура работает и на экране блокировки, и в окне установки PIN, где вводит
в то поле, которое было в фокусе последним. Виджет имеет `Qt::NoFocus`, поэтому
не перехватывает фокус и не мешает вводу с обычной клавиатуры. Показ клавиатуры
управляется переключателем в разделе NovaGram и включён по умолчанию.

При неверном PIN поле в режиме NovaGram очищается, а не выделяется, как в
upstream: нажатие на клавиатуре добавляет цифру в конец и не заменяет
выделение, поэтому иначе неверное значение накапливалось бы.

#### Исправление ввода мышкой

Пользователь сообщил, что в окне установки аварийного PIN текущий основной PIN
не принимался при вводе экранной клавиатурой, но принимался с физической.
Исправлено тремя изменениями, каждое из которых закрывает свою причину:

1. клавиатуре явно задан `Qt::NoFocus`. Иначе нажатие могло увести фокус с
   поля, и следующая цифра уходила не туда, куда смотрел пользователь;
2. поле-получатель определяется по фактическому фокусу в момент нажатия, а не
   только по запомненному сигналу `focused()`. Запомненное значение осталось
   запасным вариантом;
3. при проверке читается `text()`, а не `getLastText()`. Второе обновляется
   собственной обработкой правки поля, поэтому значение, вставленное
   программно, могло в нём отсутствовать — а именно так и вставляет цифры
   экранная клавиатура.

Третья причина объясняет и разницу между мышью и физической клавиатурой:
набранное вручную значение проходит через обработку правки и попадает в
`getLastText()`, а вставленное клавиатурой — нет.

### Русский текст при вводе

**Статус:** `Реализовано`

Тексты экрана блокировки и экранов настройки PIN не берутся из
`lang.strings`, а заданы в `Telegram/SourceFiles/novagram/nova_pin.cpp`. Причины:

1. языковой пакет Telegram может быть недоступен или неполон до разблокировки,
   и экран блокировки показывал английские строки;
2. добавление ключей в `lang.strings` перестраивает `lang_auto.h`, а значит
   практически весь проект, и увеличивает конфликты при обновлении upstream.

Язык выбирается в `NovaGram::UseRussianTexts()`: русский, если идентификатор
языка начинается с `ru`, либо если идентификатор ещё неизвестен, а системная
локаль — русская. Иначе английский.

## Запрет снимков и записи экрана

**Статус:** `Реализовано`

Каждое окно NovaGram исключается из захвата экрана через
`SetWindowDisplayAffinity` с флагом `WDA_EXCLUDEFROMCAPTURE`: снимок экрана,
запись и демонстрация экрана не видят содержимое. На системах старше
Windows 10 2004 флаг недоступен, и применяется `WDA_MONITOR` — запись получает
чёрный прямоугольник вместо содержимого.

Реализация — `Telegram/SourceFiles/novagram/nova_screen_guard.cpp`. Фильтр
событий приложения ставится до создания первого окна, поэтому ни одно окно не
успевает появиться незащищённым. Это важно: защита, включённая после показа
окна, оставляет окно доступным для захвата в промежутке.

Переключатель в разделе NovaGram включён по умолчанию. Отключение нужно для
демонстрации экрана и для отладки интерфейса.

Честные границы: защита не действует против камеры, направленной на монитор,
против программ уровня ядра и против скриншота, сделанного на другом
устройстве. Она защищает от обычных средств захвата, а не от физического
наблюдения.

## Предложение установить PIN после входа

**Статус:** `Реализовано`

Раньше после авторизации PIN не предлагался вообще, и пользователь оставался
без защиты локальных данных, пока сам не находил настройку. Теперь после входа
в первичном окне показывается диалог с объяснением, что локальные данные пока
не зашифрованы отдельным PIN, и двумя вариантами: установить PIN или отказаться.

Отметка об ответе пишется в настройки **до** показа диалога. Это защищает от
двух проблем сразу: второе окно, открывающееся одновременно, не показывает
второй такой же диалог, а падение до ответа не превращает предложение в
повторяющееся навязчивое окно.

## Раздел настроек NovaGram

**Статус:** `Реализовано`

Все настройки NovaGram собраны в один раздел `Настройки → NovaGram`, а не
разбросаны по чужим разделам upstream. Так пользователю видно, что именно
добавляет форк, а обновление до новых версий tdesktop затрагивает меньше файлов.

Раздел реализован как `Settings::Section<NovaGramSection>` в
`Telegram/SourceFiles/novagram/nova_settings.{h,cpp}` и содержит:

- **Защита**: кнопка PIN с текущим состоянием в подписи, переключатель экранной
  клавиатуры и пояснения;
- **Отправка сообщений**: главный переключатель ночного беззвучного режима и
  раскрывающийся блок области применения.

Раздел намеренно не регистрируется в поиске по настройкам через
`Builder::BuildHelper`: его `SectionMeta` требует `tr::phrase<>`, то есть ключ
из `lang.strings`, а добавление ключей перестраивает `lang_auto.h` и
практически весь проект. Вместо этого используется прямой
`SectionBuildMethod`, а заголовок берётся из `NovaGram::SettingsSectionTitle()`.
Следствие: пункты раздела не находятся поиском по настройкам — это осознанный
размен, а не недоработка.

## Беззвучные сообщения в ночное время

**Статус:** `Реализовано`

С 22:00 до 07:00 по локальному времени устройства исходящие сообщения
отправляются с признаком `silent`: получатель видит сообщение как обычно, но не
получает звук уведомления. Функция выключена по умолчанию и включается в
`Настройки → NovaGram → Беззвучные сообщения ночью`.

Настройки:

- главный переключатель, значение по умолчанию — выключено;
- отдельные переключатели области применения: личные диалоги, группы, каналы;
  все три включены, но действуют только при включённом главном переключателе.

Реализация опирается на единственную существующую точку принятия решения
`ShouldSendSilent` в `Telegram/SourceFiles/history/history_item_helpers.cpp`.
Её вызывают все пути отправки: обычные сообщения, медиа, альбомы, опросы,
списки задач, пересылка и `ApiWrap`. Поэтому добавлено ровно одно условие, и
ни один путь отправки не остаётся неохваченным.

Границы поведения, которые нужно честно сообщать пользователю:

- признак `silent` влияет только на уведомление у получателя, а не на
  доставку, содержимое или видимость сообщения;
- окно ночного времени вычисляется в момент фактической отправки, поэтому
  отложенное сообщение получает признак по времени отправки, а не создания;
- используется локальное время устройства, а не часовой пояс собеседника;
- Telegram уже применяет собственные правила беззвучных публикаций в каналах
  (`silentPosts`), и NovaGram их не отменяет, а только добавляет своё условие.

Настройки хранятся в общем KV-хранилище `Core::Settings` (`writePref<bool>` и
`readPref<bool>`), а не в бинарном потоке настроек, поэтому порядок полей при
обновлении не нарушается. Ключи: `novagram_night_silent`,
`novagram_night_silent_users`, `novagram_night_silent_groups`,
`novagram_night_silent_channels`.

Важное следствие: `Core::Settings::resetOnLastLogout()` очищает `_prefs`,
поэтому после выхода из последнего аккаунта настройки ночного режима
сбрасываются к значениям по умолчанию. Это приемлемо для необязательной
функции удобства, но должно быть учтено, если функция станет частью политики.

## Формат `tdata/novagram_pin`

Версия 2, `QDataStream` версии `Qt_5_15`, запись через `QSaveFile`:

```text
quint32 magic = 0x4E56504E ("NVPN")
qint32  version = 2
qint32  pinModeEnabled
QByteArray emergencySalt
QByteArray emergencyVerifier
qint32  emergencyIterations
qint32  failedAttempts
qint64  lockoutStartedMs
qint64  lockoutDeadlineMs
qint32  shuffledKeypad   // добавлено в версии 2
```

Файлы версии 1 читаются без потерь: `shuffledKeypad` получает значение по
умолчанию «включено». Файл, который существует, но не разбирается, трактуется
как «режим PIN включён, аварийный PIN отсутствует». Это не даёт повреждению
файла молча вернуть приложение к upstream-поведению, но и не блокирует доступ:
локальные данные защищены самим passcode.

## Версия Qt: обязательное соответствие официальной сборке

**Статус:** `Реализовано`

NovaGram Desktop собирается **тем же Qt, что и официальный клиент** — на
Windows x64 это Qt 5.15.19, а не Qt 6. Это не вопрос вкуса: выбор Qt меняет то,
как приложение выглядит и как оно себя ведёт.

Правило задано самим upstream в `Telegram/build/qt_version.py`: на `win32` без
флага `qt6` выбирается Qt 5.15.19, и именно так собирается официальный клиент.
Сборка NovaGram обязана повторять этот выбор:

```bash
scripts/build-desktop.ps1 -Config Release
```

Флаг `-Qt6` переключает сборку на Qt 6.11.1 и **не должен использоваться** для
выпускаемых сборок. Что ломается при сборке с Qt 6:

- **отрисовка шрифтов.** Qt 6 растеризует текст через DirectWrite с другой
  гаммой и сглаживанием, Qt 5 — через путь GDI. При одном и том же шрифте
  Segoe UI Semibold и одном масштабе текст в Qt 6 выглядит тоньше и светлее,
  чем в официальном клиенте. Подбор начертания при этом правильный: проверено
  логом `QT_LOGGING_RULES=qt.text.font.match.debug=true`, семейство выбирает
  начертание DemiBold даже при запросе обычной насыщенности. Дело именно в
  растеризации, а не в подборе шрифта;
- **плавность окна.** Qt 6 рисует через QRhi поверх D3D11, что видно в логе по
  строкам `RHI: Probe backend=D3D11` и `Renderer: [QRhi] (Window)`.
  Перетаскивание окна при этом заметно отстаёт от официального клиента.

Обе разницы пользователь наблюдал напрямую, сравнивая NovaGram и официальный
клиент на одной машине с одинаковым шрифтом и масштабом.

### Ловушка при переключении версии Qt

Каталог сборки помнит, каким `moc` сгенерированы файлы автогенерации. Если
переключить версию Qt, не очистив каталог, сборка падает с
`fatal error C1189: This file was generated using the moc from 5.15.19`
или с симметричным сообщением про Qt 6. Перед сменой версии Qt каталог `out`
нужно очистить.

Очищать `out` следует **вручную, сохраняя `tdata`**. Штатный флаг
`-ForceConfigure` для этого не подходит: он удаляет из `out` всё, кроме
каталогов, начинающихся с `debug` и `release`, то есть вместе с мусором сборки
уносит и рабочий профиль `out/tdata` с авторизованным аккаунтом.

## Проектные решения по следующим функциям

Раздел фиксирует принятые решения до начала реализации, чтобы обе платформы
вели себя одинаково.

### Автоудаление отправленных сообщений

- Срок настраивается от 24 до 168 часов, шаг — час; значение по умолчанию 168
  часов, то есть неделя.
- Отсчёт идёт **от момента отправки сообщения**, а не от получения и не от
  прочтения собеседником. Это единственный момент, который клиент знает точно
  и который не зависит от поведения собеседника.
- Схема удаления двухшаговая: сначала сообщение редактируется в «.» или в
  выбранный пользователем смайл, затем удаляется. Смысл шага с точкой в том,
  что у собеседника и на сервере последняя версия текста перестаёт быть
  содержательной ещё до удаления, а уведомление о редактировании выглядит
  обыденно.
- Включено по умолчанию для всех чатов, отключается для конкретного чата.
- В чатах, где у аккаунта есть права модератора, администратора или владельца,
  автоудаление по умолчанию **не применяется**: там сообщения чаще являются
  частью управления сообществом. Включить вручную можно.
- Сообщения, отправленные до включения функции, удаляются не сразу: срок для
  них отсчитывается от момента включения функции, а не от их отправки.
- Требуется локальный планировщик, переживающий перезапуск: очередь заданий
  хранится рядом с состоянием NovaGram и обрабатывается при старте и по
  таймеру. Неудачные попытки (нет сети, истёк срок редактирования на сервере,
  сообщение уже удалено) должны повторяться и не терять очередь.
- Если сообщение уже нельзя отредактировать, шаг с точкой пропускается и
  сообщение просто удаляется. Решение пользователя от 2026-08-03: удаление
  важнее маскировки, невозможность правки не должна оставлять сообщение жить.
- Честная граница: Telegram ограничивает срок, в течение которого сообщение
  можно редактировать и удалять у собеседника. Для части сообщений двухшаговая
  схема выполнима не полностью, и это нужно показывать пользователю, а не
  умалчивать.

#### Отклонено: подстраховка штатным автоудалением Telegram

**Решение пользователя от 2026-08-03: не реализовывать.** Идея обсуждалась и
была реализована, после чего отклонена и код удалён. Ниже сохранены и разбор, и
причина отказа, чтобы к этому не возвращались по кругу.

Причина отказа одна и достаточная: **штатное автоудаление Telegram чистит всю
историю чата по сроку, включая сообщения собеседника.** Обещание NovaGram
касается только исходящих сообщений пользователя. Уничтожать чужие сообщения —
это другая функция с другими последствиями, и пользователь её не хочет.

Вторая причина, менее весомая, но существенная: включение штатного
автоудаления добавляет в чат служебное сообщение вида «N включил автоудаление
через неделю», то есть объявляет собеседнику о применяемой политике.

Следствие, которое остаётся честной границей функции: локальный планировщик
работает только при запущенном NovaGram. Если устройство не в сети дольше
срока, сообщения не будут удалены, пока приложение не запустится снова. Это
принятый размен в пользу того, чтобы не трогать чужие сообщения.

#### Разбор отклонённой схемы (для истории)

Решение пользователя от 2026-08-03. Локальный планировщик работает только когда
приложение запущено. Если устройство больше недели не в сети, сообщения не
будут удалены ни на сервере, ни у собеседника. Поэтому дополнительно
включается **штатное автоудаление Telegram** (`messages.setHistoryTTL`) на тот
же срок: сервер удалит сообщения сам, независимо от того, включено ли
устройство.

Два последствия, которые обязаны быть показаны пользователю до включения,
потому что они меняют не только его чат:

1. **Собеседник это видит.** Включение штатного автоудаления добавляет в чат
   служебное сообщение вида «N включил автоудаление через неделю». Скрытной эта
   мера не является.
2. **Удаляются сообщения обеих сторон.** Штатное автоудаление Telegram чистит
   всю историю чата по сроку, а не только исходящие сообщения. Это шире, чем
   локальное автоудаление NovaGram, которое трогает только свои сообщения.

Уточнение к исходной формулировке пользователя: в обычных чатах отсчёт
штатного автоудаления идёт **от момента отправки**, а не от прочтения. От
прочтения счётчик стартует в секретных чатах, которых в Telegram Desktop нет.
Для замысла это лучше: срок совпадает с локальным сроком NovaGram, и две схемы
не расходятся.

Из-за обоих последствий штатное автоудаление выносится в отдельный
переключатель рядом с основным и не включается молча вместе с ним.

### Автоудаление: что реализовано

**Статус:** `Реализовано` (ядро), ручная проверка не выполнялась.

Модуль `Telegram/SourceFiles/novagram/nova_autodelete.{h,cpp}`.

Состояние (настройки, правила по чатам, очередь заданий) хранится через
штатный пер-аккаунтный `Storage::Account::writePref<QByteArray>`. Это
сознательный выбор вместо собственного файла: prefs аккаунта уже лежат в
зашифрованном блобе со случайным именем, а отдельный файл выдал бы наличие
функции самим именем. Для этого в `storage_account.cpp` добавлена
специализация `QByteArray` — ровно там, где upstream оставил комментарий
«Define your own pref types in the similar way».

Как работает планировщик:

- при отправке сообщение попадает в очередь со сроком «дата отправки + период»;
- сразу после отправки идентификатор ещё клиентский, поэтому подписка на
  `itemIdChanged()` заменяет его на серверный, когда сервер отвечает. Это
  тонкое место: фильтр по `isRegular()` в момент `newItemAdded()` пропустил бы
  вообще все отправляемые сообщения, потому что отправляемое сообщение
  локальное по определению;
- по таймеру раз в минуту обрабатывается не больше пяти просроченных заданий,
  чтобы не упереться в ограничения сервера;
- текстовое сообщение, которое ещё можно редактировать (`allowsEdit`),
  заменяется на «.», через минуту удаляется у обеих сторон;
- медиа, пустые тексты и сообщения вне окна редактирования удаляются сразу:
  правка подписи оставила бы само медиа на месте;
- любая ошибка редактирования ведёт к удалению, а не к отказу от него;
- очередь переживает перезапуск, потому что пишется при каждом изменении.

Настройки в `Настройки → NovaGram → Автоудаление своих сообщений`: включение,
срок (24, 48, 72, 120, 168 часов) и подстраховка штатным автоудалением.

Переопределение для конкретного чата добавлено в меню с тремя точками
(`Filler::addNovaAutoDelete` в `window/window_peer_menu.cpp`). Выбор
записывается явным правилом `Always` или `Never`, а не переключением флага:
иначе получение или потеря прав администратора молча меняла бы то, что выбрал
пользователь.

Подстраховка штатным автоудалением Telegram была реализована и затем удалена по
решению пользователя — разбор в разделе выше.

### Erase evidence

Разведка API выполнена 2026-08-12, реализация не начата. Найденное:

- перебор своих сообщений на сервере — `Api::MessagesSearch`
  (`api/api_messages_search.h`): создаётся на `History`, `Request::from`
  задаёт отправителя, страницы забираются через `searchMore()`, результат
  приходит в `messagesFounds()` как `MessageIdsList`;
- **ограничение, которое меняет замысел:** `Request::from` превращается в
  `f_from_id` только когда собеседник не пользователь. В личном диалоге
  отфильтровать по отправителю на сервере нельзя, поэтому там придётся брать
  всю историю за период и отбирать свои сообщения на клиенте по `out()`;
- свои реакции — `HistoryItem::chosenReactions()` и
  `HistoryItem::toggleReaction(reaction, source)` (повторный вызов снимает
  реакцию);
- **вторая честная граница:** серверного способа получить список «где я
  ставил реакцию» нет. Снятие реакций возможно только по загруженным в память
  сообщениям, то есть по тому, что пользователь пролистал. Это нужно прямо
  сказать в окне подтверждения, а не делать вид, что вычищены все реакции;
- удаление и замена на точку переиспользуют логику модуля автоудаления.

- Вызов из меню чата по кнопке с тремя точками.
- Выбор периода: 24 часа, неделя, месяц, всё время.
- Что уничтожается: свои сообщения по схеме «изменить на точку, затем
  удалить», свои реакции, голосовые сообщения, видеосообщения-кружки и ранее
  отправленные файлы.
- Операция ручная и необратимая, поэтому требует явного подтверждения с
  перечислением того, что именно будет уничтожено.

#### Что реализовано

Модуль `Telegram/SourceFiles/novagram/nova_erase.{h,cpp}`, пункт
`Filler::addNovaEraseEvidence` в меню чата.

Перебор истории идёт напрямую через `MTPmessages_GetHistory` страницами по 100
сообщений, а не через `Api::MessagesSearch`. Причина — ограничение из разведки
выше: в личном диалоге сервер не умеет фильтровать по отправителю, поэтому
единый путь «взять страницу истории и отобрать свои по `out()`» работает
одинаково во всех типах чатов, а поиск работал бы только в группах и каналах.

Страницы прогоняются через `processMessages(..., NewMessageType::Existing)`
намеренно: шагу замены текста на точку нужен настоящий `HistoryItem`, иначе вся
пачка выродилась бы в простое удаление без маскировки.

Найденные сообщения передаются в очередь модуля автоудаления через
`NovaGram::EnqueueNow` со сроком «сейчас». Это переиспользует уже работающий и
проверенный путь: двухшаговое уничтожение, обработка ошибок правки, живучесть
очереди при перезапуске. Чтобы ручная команда не растянулась на часы, интервал
опроса очереди при наличии просроченных заданий снижен с минуты до пяти секунд.

Снятие реакций выполняется только по загруженным в память сообщениям — это та
самая вторая честная граница из разведки, и она прямо написана в окне выбора
периода, а не умалчивается.

### Скрытие статуса прочтения

**Статус:** `Реализовано`, ручная проверка не выполнялась.

- Для новых диалогов, начатых собеседником, подтверждение прочтения не
  отправляется. Настройка включена по умолчанию.
- Отключение для конкретного диалога необратимо: вернуть скрытие в этом
  диалоге нельзя, потому что подтверждение прочтения уже ушло на сервер и
  собеседник уже увидел изменение поведения.

Модуль `Telegram/SourceFiles/novagram/nova_read_status.{h,cpp}`.

Гейт стоит в единственной точке отправки подтверждений —
`Data::Histories::readInboxTill`, сразу после
`clearIncomingFromHistory`. Место выбрано не случайно: выход именно оттуда
всё равно выполняет `syncGuard` выше по функции, поэтому диалог локально
выглядит прочитанным, а на сервер не уходит ничего.

Признак «диалог начали не вы» вычисляется один раз, по первому же сообщению в
переписке, и сохраняется навсегда. Пересчитать его позже нельзя: к тому моменту
пользователь уже ответил, а начало переписки может быть не загружено.

Правило хранится в пер-аккаунтном зашифрованном хранилище, как и остальное
состояние NovaGram, потому что список диалогов с особым режимом — это тоже
метаданные переписки.

Существующие до включения функции диалоги не затрагиваются: у них нет записи, а
запись появляется только при первом входящем сообщении в новом диалоге.

**Побочный эффект, который обязателен к показу пользователю:** для Telegram
сообщения остаются непрочитанными. Счётчик непрочитанного в таком диалоге может
возвращаться после перезапуска и виден на других устройствах. Это записано и в
разделе настроек, и в окне самого диалога.

**Чего ещё нет:** отдельной постоянной кнопки вверху справа в диалоге. Сейчас
вход в описание и необратимое отключение находится в меню чата с тремя точками,
то есть тоже вверху справа, но это пункт меню, а не висящая кнопка. Отдельный
элемент в `HistoryView::TopBarWidget` — следующий шаг по этой функции.

## Что делать дальше

Порядок отражает приоритет.

1. **Автоудаление отправленных сообщений** по решению выше — выбран как
   следующий крупный этап. Начинать с локального планировщика и хранилища
   очереди, потом настройки чатов, потом двухшаговое удаление.
2. **Ручная проверка непроверенного.** Экранная клавиатура: перемешивание при
   каждом показе, ввод мышкой, «Стереть» и «Ввод», отсутствие перехвата фокуса.
   Раздел `Настройки → NovaGram`: подпись состояния PIN, раскрытие блока
   области применения ночного режима. Запрет системной разблокировки:
   при включённом PIN на экране блокировки не должно быть ни кнопки Windows
   Hello, ни автоматического запроса, а переключатель в разделе passcode должен
   исчезнуть. Отсчёт блокировки: три неверных PIN, затем перезапуск процесса —
   отсчёт обязан продолжиться, а не обнулиться.
3. **Ночной беззвучный режим на реальном чате.** Включить, дождаться окна
   22:00–07:00 либо временно перевести часы, отправить сообщение в личный чат,
   группу и канал и убедиться, что у получателя нет звука уведомления.
4. **Аварийный PIN в разблокированной сессии.** Сейчас физическое удаление
   работает только на холодном старте: при автоблокировке работающей сессии
   базы кэша открыты и Windows не даёт их удалить. Нужен путь «закрыть базы →
   удалить → перезапустить приложение». До этого — предупреждать пользователя,
   что полное уничтожение гарантировано именно при заблокированном запуске.
5. **Проверка длины при вводе основного PIN на экране блокировки.** Сейчас поле
   ограничено шестью символами, но upstream-passcode может быть длиннее, если он
   был задан до включения режима PIN. Добавить миграцию или предупреждение.
6. **Аппаратная привязка `tdata/novagram_pin`** через DPAPI с флагом
   `CRYPTPROTECT_LOCAL_MACHINE` либо через TPM, чтобы состояние блокировки
   нельзя было сбросить копированием или удалением файла.
7. **Режим заглушки после аварийного PIN.** Сейчас приложение после уничтожения
   данных показывает обычный экран входа. Android планирует постоянную локальную
   заглушку; для desktop это отдельный этап.
8. **Очистка `log.txt` при аварийном PIN.** Журнал лежит вне `tdata`, открыт
   приложением и после уничтожения данных остаётся свидетельством того, что
   аккаунт был подключён. Нужен безопасный путь усечения без поломки логгера.
9. **Автотесты.** В desktop-репозитории нет модульных тестов для этих модулей.
   Нужны тесты формулы блокировки, отката часов, чтения файла версии 1 в
   версии 2, равномерности перемешивания клавиатуры и того, что аварийный PIN
   не совпадает с основным.
10. **Настраиваемые границы ночного окна.** Сейчас 22:00–07:00 заданы
   константами `kNightSilentFromHour` и `kNightSilentTillHour`. Следующий шаг —
   выбор времени пользователем и, возможно, отдельные исключения для чатов.
11. **Переопределения ночного режима для отдельных чатов**, по аналогии с
    планом переопределений политики скриншотов на Android.
12. **Перенос остальных Android-функций**: отключение звонков, политика
    скриншотов, строгий DoH, транспорт Cloudflare WSS, очистка метаданных.

## Критерии допуска к релизу

Функция получает статус `Проверено` только после выполнения всех применимых
условий:

1. Проходят проверки чистой установки и обновления существующего `tdata`.
2. Проходит проверка принудительного завершения процесса и перезагрузки во
   время активной задержки.
3. Повреждённое состояние обрабатывается безопасно и не раскрывает открытый текст.
4. Пользовательский текст точно описывает локальные, удалённые и условные эффекты.
5. Подтверждена совместимость с текущим официальным upstream tdesktop.
6. Этот документ обновлён в том же изменении.
